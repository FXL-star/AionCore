# 助手分类与执行引擎关系说明

## 问题背景

用户问题：项目中助手的概念，是如何区分“自定义助手”、“CLI 助手”、“官方助手”的？

## 结论

**这三类按“助手是怎么产生的”区分，不是按“使用什么模型或执行引擎”区分。**

本文后端源码路径以 **AionCore 仓库根目录**为基准；前端源码路径以**相邻 AionUi 仓库根目录**为基准，并在引用处注明。

## 三类助手的对应关系

| 界面分类 | 助手 `source` | 来源与含义 |
|---|---|---|
| **自定义助手** | `user` | 用户创建的助手，保存自己的名称、配置及绑定 Agent |
| **CLI 助手** | `generated` | 后端根据符合条件的 Agent，自动生成的助手入口 |
| **官方助手** | `builtin` | 项目随程序提供的 21 个内置助手 |

官方助手名单见同目录文档：[后端默认助手名单与存储说明](./后端默认助手名单与存储说明.md)。

后端枚举：`crates/aionui-api-types/src/assistant.rs:30`。

前端也直接按这个字段分组，以下两处均为**相邻 AionUi 仓库**中的路径：

- 自定义、CLI 分组：`packages/desktop/src/renderer/pages/settings/AssistantSettings/assistantUtils.ts:166`。
- 官方助手页：`packages/desktop/src/renderer/pages/settings/AssistantSettings/home/OfficialAssistantsGrid.tsx:44`。

## 后端如何形成这三类

### 自定义助手：用户创建，来源固定为 user

创建时可以指定 `agent_id`，但绑定哪个 Agent 不会改变助手的分类。写入定义时固定设置 `source = "user"`、`owner_type = "user"`。

代码位置：`crates/aionui-assistant/src/service.rs:759`。

### CLI 助手：系统从 Agent 自动派生

后端筛选启用、满足安装/可用标记、支持新会话且状态符合要求的 Agent，再生成助手。生成身份以 `bare:<Agent ID>` 为基础，设置 `source = "generated"`，名称和绑定关系跟随该 Agent。

代码位置：`crates/aionui-assistant/src/service.rs:546`、`crates/aionui-assistant/src/service.rs:604`。

### 官方助手：从内置清单加载

遍历内置助手清单，写入 `source = "builtin"`、`owner_type = "system"`。

代码位置：`crates/aionui-assistant/src/service.rs:251`。

## 最容易混淆的地方

**“助手来源”和“执行它的 Agent”是两个独立维度：**

- `assistant.source`：决定它属于自定义、CLI、官方哪一类。
- `assistant.agent_id`：决定由哪个 Agent 执行。
- `assistant.agent.source`：表示 **Agent 自身的来源**，不是助手分类。

结构见：`crates/aionui-api-types/src/assistant.rs:36`。

因此：

- **自己创建一个绑定 CLI Agent 的助手，仍然是“自定义助手”**，不会自动归入 CLI 分组。
- **官方助手改绑 CLI Agent，仍然是“官方助手”**。后端允许通过用户覆盖配置修改绑定。见 `crates/aionui-assistant/src/service.rs:1269`。
- **CLI 分组也不严格等于“外部 CLI 工具”**：自动生成条件支持 `Acp`、`Aionrs`、`Antigravity`，所以内部 `Aionrs` 满足条件时也可生成这一类助手。见 `crates/aionui-common/src/enums.rs:60`。

## 简要总结

**用户创建的是自定义助手，Agent 自动派生的是 CLI 助手，项目内置的是官方助手；用哪个引擎执行，另看 `agent_id`。**

本文仅整理已核验的源码解答，不涉及新增实现，也不代表已运行测试或检查当前实际数据库。
