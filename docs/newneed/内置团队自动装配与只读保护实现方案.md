# 内置团队（Builtin Team）自动装配与只读保护实现方案

> 目标：像内置助手（builtin assistant）一样，用一个「内置团队元数据」清单，在安装/启动后自动装配出一支内置团队；并在数据层、API 层与前端三处都区分「系统内置」与「用户自定义」，前端对内置团队禁止删除团队、添加/移除成员等修改操作。

---

## 1. 背景与目标

当前 AionCore 已有成熟的「内置助手」机制：把 `assistants.json` 编译进二进制，启动时物化到数据库，并用 `source = "builtin"` 标识。团队（team）目前**没有**等价机制——团队只能由用户（或 MCP）运行时创建，`teams` 表没有「内置/自定义」标识，前端也不区分。

本方案要交付三件事：

1. **内置团队元数据 + 启动自动装配**：新增 `builtin-teams/teams.json` 清单、一个内置团队注册表，启动时幂等地把清单物化成团队（含成员会话装配）。
2. **内置标识**：`teams` 表新增 `source` / `source_ref` 列，`TeamResponse` 暴露 `is_builtin`，用于区分「系统内置」与「自定义」。
3. **只读保护**：后端对内置团队的增删改做硬校验（防御性），前端在团队展示处按 `is_builtin` 禁用删除团队、添加/移除成员等修改入口。

## 3. 总体设计

对齐内置助手的「清单 → 注册表 → 启动物化 → 来源标识」链路，团队侧新增一条同构链路：

```
crates/aionui-app/assets/builtin-teams/teams.json
        │  include_dir! 编译进二进制
        ▼
aionui-team::builtin::BuiltinTeamRegistry::load()   （镜像 BuiltinAssistantRegistry）
        │
        ▼
TeamSessionService::materialize_builtin_teams()     （启动时幂等物化）
        │  source="builtin", source_ref=builtin.id
        ▼
teams 表（新增 source/source_ref 列）→ Team → TeamResponse.is_builtin → 前端 TTeam.is_builtin
```

关键取舍：

- **来源标识用字符串 `source`（`"builtin" | "user"`）+ `source_ref`，而不是布尔列**。与助手 `assistant_definitions.source/source_ref` 语义一致，且 `source_ref` 是幂等装配（重启后不重复建）和「清单移除后软删」的锚点。前端用派生布尔 `is_builtin = (source == "builtin")` 做渲染判断。
- **成员复用现有 `TeamAgentInput`**（`crates/aionui-api-types/src/team.rs:49`），清单里的 `agents` 与 `CreateTeamRequest.agents` 同构，直接复用 `provision_initial_agents`（`crates/aionui-team/src/provisioning.rs:235`）完成「成员会话」装配。
- **只读保护做两层**：后端在 `remove_team/rename_team/add_agent/remove_agent` 里硬校验（防绕过前端）；前端按 `is_builtin` 隐藏/禁用入口（用户体验 + 不产生后端 403）。

## 4. 分阶段实现方案

### 阶段 1：内置团队元数据清单与注册表（后端）

**1a. 新增清单文件** `crates/aionui-app/assets/builtin-teams/teams.json`：

```json
{
  "version": "1.0.0",
  "teams": [
    {
      "id": "builtin-office-suite",
      "sort_order": 0,
      "default_enabled": true,
      "name": "Office Suite",
      "name_i18n": { "en-US": "Office Suite", "zh-CN": "办公套件团队" },
      "description": "A ready-made team for Word / PPT / Excel document work.",
      "description_i18n": { "zh-CN": "面向 Word / PPT / Excel 文档工作的开箱即用团队。" },
      "workspace_mode": "shared",
      "agents": [
        { "assistant_id": "word-creator", "role": "lead",      "name": "Word 助手" },
        { "assistant_id": "ppt-creator",   "role": "teammate", "name": "PPT 助手" },
        { "assistant_id": "excel-creator", "role": "teammate", "name": "Excel 助手" }
      ]
    }
  ]
}
```

说明：
- `id` 是稳定唯一键（作为 `source_ref` 锚点），沿用内置助手的短横线命名风格。
- `agents` 与 `TeamAgentInput` 同构（`name/role/backend?/model/assistant_id?`），**必须恰好一个 `lead`/`leader`**（由 `provision_initial_agents` 校验）。
- `assistant_id` 引用内置助手 id（如 `word-creator`），装配时由现有助手目录解析后端/模型。

**1b. 新增注册表** `crates/aionui-team/src/builtin.rs`（镜像 `aionui-assistant/src/builtin.rs`）：

### 阶段 2：数据层新增来源标识 + 迁移

**2b. 行模型** `crates/aionui-db/src/models/team.rs:8` 的 `TeamRow` 增加：

> 涉及所有 `TeamRow { .. }` 字面量构造点（`service.rs` 的 `create_team`、`types.rs` 测试、`test_utils.rs` 等）同步补齐字段。

**2c. 领域类型** `crates/aionui-team/src/types.rs:157` 的 `Team` 增加 `pub source: String`（+ 可选 `source_ref`），并提供：

`Team::from_row`（`:287`）从 `row.source` 读取；`Team::to_response`（`:300`）同步。

### 阶段 3：启动自动装配（幂等物化）

在 `TeamSessionService` 新增（或新增模块 `service/materialize.rs`）：

```rust
pub async fn materialize_builtin_teams(&self, user_id: &str) -> Result<(), TeamError>
```

逻辑（对齐 `materialize_builtin_definitions`）：

1. 遍历 `BuiltinTeamRegistry::all()`。
2. 用 `source_ref == builtin.id` 查是否已存在内置团队行（**需要新增 repo 方法** `get_team_by_source_ref`，见 3a）。
   - 已存在且 `archived_at IS NULL`：跳过（幂等）。
   - 已存在但被归档（`archived_at` 非空）：清空 `archived_at` 恢复（对齐助手「软删后按 source_ref 复活」的行为）。
3. 不存在：调用 `provision_initial_agents(user_id, team_id, &builtin.agents, None)` 完成成员会话装配，然后持久化 `TeamRow`，其中 `source = "builtin"`、`source_ref = Some(builtin.id)`。
4. 广播 `team.created`（复用 `broadcast_team_created`），让前端列表自动刷新。

**3a. 新增仓库方法**（`crates/aionui-db/src/repository/team.rs` 的 `ITeamRepository` + `sqlite_team.rs` 实现）：

```rust
async fn get_team_by_source_ref(&self, source_ref: &str) -> Result<Option<TeamRow>, DbError>;
```

**3b. 装配接线**：在 `crates/aionui-app/src/router/state.rs` 构造完 `TeamSessionService` 后调用 `materialize_builtin_teams`，并在 `state.rs` 里构造 `BuiltinTeamRegistry::load()` 注入服务（对齐 `state.rs:451` 的助手注册表注入）。具体插入点在启动顺序中的位置需在实现时按 `TeamSessionService` 构造时机精确定位（不要早于 DB 与助手目录就绪）。

**3c. 幂等性 & 失败语义**：
- 单个内置团队物化失败应 `warn!` 并跳过，不阻断整个启动（对齐助手 `sync_legacy_user_assistants` 的「跳过脏数据」策略）。
- 装配会为每个成员创建会话（比助手的纯行物化重），故启动耗时需在方案落地时评估；若成员解析失败（如引用不存在的助手），按 `provision_initial_agents` 的既有错误处理走 `warn` + 跳过该团队。

### 阶段 4：后端只读保护（防御性校验）

**4a. 新增错误变体**（`crates/aionui-team/src/error.rs` 的 `TeamError`）：

```rust
#[error("built-in teams are read-only and cannot be modified")]
BuiltinTeamImmutable,
```

在 `routes.rs` 的 `From<TeamError> for ApiError` 里映射为 `ApiError::Forbidden(...)`（或带 code 的 `coded(403, "BUILTIN_TEAM_IMMUTABLE", ...)`，便于前端/测试断言具体错误码）。

**4b. 在修改入口统一加校验**。提供一个私有辅助：

```rust
async fn ensure_team_mutable(&self, user_id: &str, team_id: &str) -> Result<Team, TeamError> {
    let team = self.load_owned_team(user_id, team_id).await?;
    if team.is_builtin() {
        return Err(TeamError::BuiltinTeamImmutable);
    }
    Ok(team)
}
```

并在以下方法里，用 `ensure_team_mutable` 替换（或在其结果上追加校验）：
- `remove_team`（`service.rs:879`）——**禁止删除内置团队**
- `rename_team`（`service.rs:942`）——**禁止重命名**（属于「修改」，一并禁止）
- `add_agent`（`service.rs:959`）——**禁止添加成员**
- `remove_agent`（`service.rs:1020`）——**禁止移除成员**

> 范围说明：用户明确要求「禁止删除团队、添加/移除团队成员」；重命名同为修改类操作，建议一并禁止。其余成员级修改（`rename_agent`/`update_agent_model`/`reorder`/`set_session_mode` 等）在实现时按同一 `ensure_team_mutable` 策略评估是否纳入——若同一团队不可改，则所有写成员/团队的入口都应走同一守卫，避免出现「某个入口能改」的缺口。最终范围以评审确认。

### 阶段 5：API 响应暴露标识 + 前端类型

**5a. `TeamResponse`**（`crates/aionui-api-types/src/team.rs:587`）增加：

```rust
#[serde(default)]
pub is_builtin: bool,
```

`build_team_response`（`response_builder.rs:4`）与 `Team::to_response`（`types.rs:300`）都设为 `team.is_builtin()`。

**5b. 前端类型** `TTeam`（`teamTypes.ts:58`）增加 `is_builtin: boolean;`；`fromBackendTeam`（`teamMapper.ts:122`）增加：

```ts
is_builtin: (r.is_builtin as boolean | undefined) ?? false,
```

### 阶段 6：前端按 `is_builtin` 禁用修改入口

在团队展示处引入一个统一的 `teamReadOnly = team.is_builtin` 判断，逐处禁用：

- **侧栏 `TeamSiderSection.tsx`**：`menuItems`（`:222`）对内置团队**去掉 `rename` 与 `archive`**（保留 `pin`，置顶是用户偏好，非团队数据修改）；`handleArchiveTeam`/`handleRenameConfirm` 入口加 `team.is_builtin` 早退或直接不渲染按钮。可加一个 Tooltip 提示「系统内置团队不可修改」。
- **团队页 `TeamPage.tsx`**：`handleRemoveAssistantWithConfirm`（`:968`）与 `handleRenameTeam`（`:997`）开头加 `if (team.is_builtin) return;`（或把 `onRenameTitle` 置空、移除成员按钮不渲染）。
- **成员胶囊 `TeamTabs.tsx`**：`memberOpsDisabled`（`:254`）改为 `warmingUp || team.is_builtin`（需把 `team` 或 `is_builtin` 传入 `TeamTabs`，或经 `TeamTabsContext`/`useTeamTabs` 提供）。这样添加成员（`:376-382`）、移除（`:352`）、改名（`:350`）、拖拽排序一并禁用。
- **列表删除 `useTeamList.ts`**：`removeTeam`（`:52`）加 `team.is_builtin` 早退（若该硬删路径仍被其他入口引用）。

**i18n**：新增/修改的用户可见文案（如「系统内置团队不可修改」的 Tooltip）必须走 i18n key，不硬编码；同步维护 `packages/desktop/src/common/config/i18n-config.json` 与 `locales/`。

## 5. 测试计划（遵循 AGENTS.md 测试规则）

### 后端（`crates/aionui-team/tests/` + `crates/aionui-app/tests/`）

- **物化 happy path**：空库启动后 `materialize_builtin_teams` 生成内置团队，`teams.source="builtin"`、`source_ref=清单id`，成员会话已装配、恰好一个 lead。
- **物化幂等**：连续跑两次，不重复创建团队（`get_team_by_source_ref` 命中后跳过）。
- **归档复活**：内置团队被归档后再物化，`archived_at` 被清空恢复。
- **只读保护 bad path（逐端点）**：对内置团队调 `remove_team / rename_team / add_agent / remove_agent`，断言返回 403 / `BUILTIN_TEAM_IMMUTABLE`（或 `BuiltinTeamImmutable`），且数据未变更。
- **自定义团队不受影响**：`source="user"` 的团队增删改成员照常成功（回归）。
- **跨用户隔离**：用户 A 不能删/改用户 B 的内置团队（复用现有 `(user_id, team_id)` 归属校验）。
- **WebSocket 事件**：物化后广播 `team.created`（若走 `broadcast_team_created`）；`remove_team` 对内置团队被拒绝时不广播 `team.removed`。

### 前端（AionUi，Vitest + 必要时 E2E）

- `fromBackendTeam` 对 `is_builtin` 缺失/true/false 的映射单测。
- `TeamTabs` 在 `is_builtin=true` 时，添加/移除/改名/排序入口禁用（可用组件测试或扩展既有 `team-member-ops` / `team-ui-details` E2E 断言 `data-testid='team-tab-add-member'`、`team-tab-remove-*` 不可用）。
- `TeamSiderSection` 内置团队不出现 `rename`/`archive` 菜单项。

## 6. 日志与可观测性（AGENTS.md Logging 要求）

- 物化链路属「启动关键路径」，需在 `info` 级别记录：物化开始/完成、创建了哪些内置团队（仅 `team_id` + `source_ref`，不含成员敏感内容）、跳过的团队数。
- 单个内置团队物化失败：`warn`（含 `source_ref` 与错误），沿用助手「跳过脏数据」的语义，不阻断启动。
- 只读保护命中：`remove_team` 等被 `BuiltinTeamImmutable` 拒绝时，可 `warn` 记录 `team_id` + 操作名，便于诊断「前端漏禁」导致的异常调用。日志不输出 `agents`/会话内容等敏感 payload。

## 7. 影响与风险 / 边界

- **启动耗时**：团队物化会创建成员会话，比助手纯行物化更重；需在实现后量测冷启动增量，必要时把物化放到后台任务或懒装配。
- **`TeamRow` 字段补齐面**：`TeamRow` 新增两列会触碰所有 `TeamRow { .. }` 构造点与 `SELECT *` 映射（`sqlx::FromRow` 要求列名与字段一致），务必全量 grep 补齐，避免遗漏导致反序列化失败。
- **迁移兼容**：`source DEFAULT 'user'` 保证存量团队自动为「自定义」，不破坏现有数据。
- **清单成员引用失效**：`assistant_id` 引用不存在/被删的内置助手时，`provision_initial_agents` 会失败；按「跳过该内置团队 + warn」处理，避免整队阻塞。
- **「移除清单中的内置团队」的软删/清理**：v1 只做「创建 + 归档复活」，是否要像助手 `soft_delete_removed_builtin_definitions` 那样对「清单已删除的内置团队」做软删/清理，作为后续项单独评估（团队含会话，删除代价更高，需产品确认）。
- **边界**：只读保护覆盖 `aionui-team` 内的修改入口；若 MCP / 其他侧支（sidebar archive 等）另有团队写路径，需一并纳入 `ensure_team_mutable` 评估。

## 8. 验收标准

1. 全新安装启动后，清单定义的内置团队自动出现在团队列表，成员按清单装配、恰好一个 leader。
2. 重启不重复创建；被归档的内置团队重启后恢复。
3. `teams` 表内置团队 `source='builtin'`、`source_ref` 指向清单 id；自定义团队 `source='user'`、`source_ref` 为空。
4. `GET /api/teams` 与 `GET /api/teams/{id}` 返回 `is_builtin`，前端 `TTeam` 正确映射。
5. 后端对内置团队的删除/重命名/添加成员/移除成员返回 403（或 `BUILTIN_TEAM_IMMUTABLE`），数据不变；自定义团队操作不受影响。
6. 前端内置团队不出现/禁用：删除团队（归档/删除）、添加成员、移除成员、（及重命名）入口。
7. 新增测试全部通过：后端物化幂等 + 只读保护 bad path + 跨用户隔离 + WS 事件；前端 mapper 与组件禁用用例通过。
